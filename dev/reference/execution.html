Polling ​

DynamicObjects.Pending Type
julia
Pending

Cheap, non-Task handle a poller (fetchindex / fetchproperty / get!(…; fetch=identity)) gets back while a value is still being computed. It points at where the value will land — a Slot (bare props) or the backing (cache, key) — plus the in-flight latch, so a caller can fetch(p) to BLOCK for the value (rethrowing if the compute failed) or ignore it and poll again later. Replaces the former "rv is a Task while in-flight" poll contract: callers now branch on rv isa Pending (still computing) vs. the value (done). The progress/status node stays optional and is never relied on for readiness.

A handle for a computation started through an executor (a Deferred selector, or the property's DynamicObjects.property_executor) carries that executor, and a blocking fetch on it waits through DynamicObjects.await_deferred.

If the computation is invalidated while in flight (clear_mem_caches!, clear_cache!, sync!, invalidate!, force=true), its value is not stored, and fetch re-resolves the access: it waits for a computation started since, or starts one. A fetch already waiting re-resolves at the invalidation, not when the invalidated computation ends.

DynamicObjects.fetchindex Function
julia
fetchindex(callback, ip, indices...; force=false, retry_failed=force, kwargs...)

Request an indexed property without blocking. The callback receives (result, status): result is a Pending handle while work is in flight, or the completed value; status is its progress node or nothing. Calling fetch on the handle blocks and rethrows a computation failure.

force=true first calls invalidate! for the requested entry, removing its memory and disk value. See that function for in-flight behavior.

source
DynamicObjects.fetchindex! Function
julia
fetchindex!(callback, ip, indices...; fetch=Base.fetch, kwargs...)

In-place variant of fetchindex. When callback is nothing, falls through to a plain memoize!(ip, indices...; fetch, kwargs...) — useful for sites that opt out of the two-phase fetch dance without changing call shape.

When callback is a Treebars.ProgressNode, the call blocks for the value. It computes inline on the caller's task, as a plain call does, and attaches the computation's node under callback, where it stays once finished; a documented cache hit attaches the entry's node noted "(cached)". With fetch=identity it polls instead and returns a Pending while the computation runs. fetchproperty! with a progress node is the blocking form for a bare property; @fetch! and @progress thread their reads through both.

source
DynamicObjects.fetchproperty Function
julia
fetchproperty(fetch, o, name::Symbol)

Like fetchindex but for bare (non-indexed) properties. Triggers computation via the PropertyCache and calls fetch(rv, status) where rv is a Pending handle (the compute is still in flight — fetch it to block for the value) or the already-computed result, and status is the substatus object or nothing.

For Dict-backed caches (serial), falls through to getproperty (synchronous, no status). The two-phase dance only applies to ThreadsafeDict-backed caches.

fetchproperty!(callback, o, name::Symbol)

In-place variant of fetchproperty. When callback is nothing, falls through to getproperty(o, name).

DynamicObjects.maybefetchindex! Function
julia
maybefetchindex!(progress, f, args...; kwargs...)

Dispatch helper used by @fetch! for call sites. The default just calls f(args...; kwargs...); the specialization for IndexableProperty preserves the property's declaration-site cache policy while attaching progress: ordinary properties route through fetchindex! (memoized + progress), while @fresh properties route through maybeprogress! (fresh + progress, with no cache read or write).

Dispatch helper used by @fetch! for property accesses. For @dynamicstruct instances, routes through fetchproperty! (cached + progress-tree attachment). For indexed properties (IPs) and non-DO objects, falls through to getproperty(o, name).

DynamicObjects.@fetch! Macro
julia
@fetch! progress expression

Thread property reads in expression through the progress-aware fetch helpers. Indexed reads use fetchindex!, scalar reads use fetchproperty!, and declaration-marked fresh properties retain their uncached policy through maybeprogress!. Non-property functions keep their ordinary call behavior.

With a Treebars progress node these reads block and attach the computation's node beneath it. With nothing they use the ordinary access path. Property bodies already attach their source-visible reads automatically.

source
DynamicObjects.@dynamic_progress Macro
julia
@dynamic_progress progress_var body

Rewrite every :call inside body as maybeprogress!(progress_var, callee, args…). Returns the rewritten body unchanged otherwise. The caller is responsible for binding progress_var — e.g. via Treebars.@progress progress_var body — and for keeping DO free of a hard Treebars dependency.

maybeprogress! dispatches on progress_var's runtime type: a Treebars.ProgressNode (when the caller has wrapped in Tb.@progress) opens per-call substatuses; noprogress opts out; anything else collapses to a plain f(args…). The macro itself doesn't care which.

In @dynamicstruct, a property marker @dynamic_progress lowers to

julia
prop() = @dynamic_progress __status__ body

where __status__ is the IP caller's bound progress context (or nothing).

Standalone:

julia
Treebars.@progress my_status begin
    @dynamic_progress my_status begin
        a = foo(x)           # → maybeprogress!(my_status, foo, x)
        b = @memo! bar(y)    # cached + progress (see `maybememoize!`)
        a + b
    end
end
source
DynamicObjects.maybeprogress! Function
julia
maybeprogress!(progress, callee, args…; kwargs...)

Runtime dispatch arm for @dynamic_progress-rewritten call sites. The rewriter wraps every call as maybeprogress!(__progress__, callee, args…), where __progress__ resolves to the current Treebars progress context (the enclosing IP's __status__ at top level; a nested @progress block re-binds it to that block's node). Dispatch on callee:

  • callee::IndexableProperty — open a per-call substatus rooted at progress, run the IP body inside it (no caching).

  • callee::typeof(noprogress) — opt-out, calls through (noprogress(f, args…)).

  • anything else — plain callee(args…; kwargs…).

The caching stack — @memo! foo(x) inside a @dynamic_progress body — lands at maybememoize!(maybeprogress!, progress, callee, args…) after natural macro expansion order, and is handled by the corresponding maybememoize! dispatch arms (see above).

progress === nothing is fine throughout — the _default_substatus / fetchindex! paths have explicit ::Nothing fallbacks.

source
DynamicObjects.noprogress Function
julia
noprogress(f, args...; kwargs...)

Opt out of dynamic progress wrapping at a specific call site. Inside an IP body annotated with @dynamic_progress, every call is rewritten to maybeprogress!(__progress__, callee, args…). Writing noprogress(f, args…) makes the rewriter emit maybeprogress!(__progress__, noprogress, f, args…), which dispatches to a method that just runs f(args…) without any progress attachment.

Note the argument shape: noprogress(f, args…) (comma-separated callee and its args), not noprogress(f(args…)) — the latter would still wrap f(args…) under the body-wide rewrite before noprogress ever sees it.

Outside a @dynamic_progress body, noprogress(f, args…) is just f(args…).

Deferred work ​

DynamicObjects.Deferred Type
julia
Deferred(executor)

A nonblocking fetch selector that schedules work through executor(work::DeferredCompute). The first caller receives a Pending handle while the work waits or runs. Use it where fetch=identity is accepted.

The executor is called after registering the in-flight entry, with no cache lock held. It should enqueue promptly, then eventually run or abandon the work under the DeferredCompute contract. A deliberately inline executor may run it immediately. Declaration-level scheduling uses DynamicObjects.property_executor; blocking waits cooperate through DynamicObjects.await_deferred.

source
DynamicObjects.DeferredCompute Type
julia
DeferredCompute

One first-arriving compute, handed to a Deferred executor. Its in-flight latch is already registered, so concurrent accessors of the same key already dedupe onto it — blocking callers wait for it, pollers receive a Pending — for as long as it sits in the executor's queue. Its progress node stays pending (·, no elapsed time) until run! starts it.

The executor must eventually call exactly one of:

  • run!(d) — run the compute on the calling task. Call it from a worker to run in the background; calling it synchronously inside the executor makes the originating get! behave like a blocking accessor — the value, not a Pending, comes back (the escape hatch for a compute started from inside one of the executor's own workers, where queueing behind yourself would deadlock).

  • abandon!(d, reason) — never run it; the key fails with ComputeAbandoned.

Only the first of the two takes effect. Dropping a DeferredCompute without calling either leaves the key in flight forever.

Whichever task calls run!, the compute runs as an undeferred compute would where it was started: under the logger current there, and with every ScopedValue set there (a layer's own request context, a with_compute_trace scope). Only the job queue's slot is the running task's own.

source
DynamicObjects.ComputeAbandoned Type
julia
ComputeAbandoned(reason)

Recorded as a key's failure when an executor abandon!s a queued compute instead of running it, or when the worker process running it (see configure_queue!) exited or was restarted (started is then true). Waiters and pollers see it like any other failure; with the default retry_failed=true the next access starts a fresh compute.

Computation traces ​

DynamicObjects.with_compute_trace Function
julia
with_compute_trace(f; events=0, invalidations=1000) -> (value, trace)
with_compute_trace(f, trace::ComputeTrace)

Run f() and record property reads in a ComputeTrace. The scope follows spawned tasks and deferred work. Nested scopes also record in the outer trace. An existing trace can collect several calls and remains available if f throws.

compute_trace_rows reports counts and times by type and property. Outcomes distinguish memory hits, memoized computations, fresh computations, disk reads, waits, pending polls and errors. Dunder-property reads and a direct fetch of a Pending handle are not recorded separately.

total_s includes nested reads; self_s subtracts reads nested on the computing task. It does not subtract time spent waiting for separately spawned tasks. hit_s includes key hashing. These are measured durations, not estimates of execution time with compilation excluded.

events retains at most that many individual reads in trace.events, holding arguments by reference. invalidations bounds the invalidation log, which records clears, entry invalidations and synchronization that drops values. The trace stops changing when all its scopes have ended.

source
DynamicObjects.ComputeTrace Type
julia
ComputeTrace(; events=0, invalidations=1000)

What property reads did while a with_compute_trace scope using it was active. Show it for a per-property table and the invalidation log; compute_trace_rows returns the table as data. Fields:

  • events::Vector{ComputeTraceEvent}: the first events reads (none by default), and events_dropped, how many more were not kept;

  • invalidations::Vector{ComputeTraceInvalidation}: the first invalidations invalidations, and invalidations_dropped.

A trace records only while one of its scopes is active, so a trace whose scopes have all ended never changes, even when a task spawned inside one of them outlives it.

source
DynamicObjects.compute_trace_rows Function
julia
compute_trace_rows(trace::ComputeTrace) -> Vector{NamedTuple}

The per-property table of a ComputeTrace as data, one row per (type, property) with type, property, calls, hits, computed, fresh, disk, waits, pending, errors and the times in seconds self_s, total_s, max_s, hit_s, wait_s (see with_compute_trace). Sorted by own time, self_s + hit_s, then by calls.
