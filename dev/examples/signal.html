Cached signal analysis ​

A synthetic voltage trace is represented by a fixed vector of samples. This example subtracts the sample mean, applies a gain, and computes the sum of squared amplitudes. The input is a small, fixed vector so that the computations and cache entries can be inspected together. No random generator, file download, or fitted model is involved. The same object structure can hold a larger trace without changing how a reader requests its derived values.

Object ​

The formulas belong to the object. A field holds the samples; properties express the dependency chain from samples to offset, centered values, scaled values, and squared amplitude. A gain is an argument to an indexed property, so each requested gain has its own cache entry.

julia
using DynamicObjects

@dynamicstruct struct Signal
    samples::Vector{Float64}
    offset = sum(samples) / length(samples)
    centered = samples .- offset
    scaled(gain::Float64) = gain .* centered
    energy(gain::Float64) = sum(abs2, scaled(gain))
end

signal = Signal([1.0, 2.0, 4.0, 5.0])
signal.samples
4-element Vector{Float64}:
 1.0
 2.0
 4.0
 5.0

The samples are in volts, gain is dimensionless, and energy here is a sum of squared voltages. It is not physical energy in joules: that would also require a sampling interval and an electrical model. The field is an input owned by this calculation. After constructing the object, leave that vector unchanged; changing its contents in place would not inform the dependency system that its derived values are obsolete.

The descriptor exposes the dependencies recorded from the property bodies without running those bodies. It provides a generated view of the definition, so changing the formula also changes this table at the next documentation build.

julia
[(name, property_descriptor(Signal, name).dependencies)
 for name in (:offset, :centered, :scaled, :energy)]
4-element Vector{Tuple{Symbol, Vector{Symbol}}}:
 (:offset, [:samples])
 (:centered, [:offset, :samples])
 (:scaled, [:centered])
 (:energy, [:scaled])

The dependency names describe declared reads. They are not a general analysis of effects inside arbitrary Julia functions. Keep the reads that define your calculation visible in the property bodies; pass explicit inputs to helpers.

Reads ​

Repeated calls with the same arguments reuse the stored array. Calls with a different gain compute a distinct result, while sharing the centered samples. The trace records what happened during this group of reads.

julia
values, trace = with_compute_trace() do
    (first = signal.scaled(2.0),
     again = signal.scaled(2.0),
     lower = signal.scaled(0.5),
     energy = signal.energy(2.0))
end
values
(first = [-4.0, -2.0, 2.0, 4.0], again = [-4.0, -2.0, 2.0, 4.0], lower = [-1.0, -0.5, 0.5, 1.0], energy = 40.0)

first and again refer to the same array. Treat that returned array as read-only; use copy before modifying it for another purpose. Otherwise a later reader would receive the edited result from the cache. The lower result uses another entry because its argument differs. energy reads the already stored scaled array instead of repeating the scaling operation.

Diagnostics ​

The trace table separates body computations from memory hits. It counts property reads rather than elapsed time, so this example makes no claim about speed. Compilation, input size, key hashing, and the cost of each formula would all affect a timing measurement.

julia
rows = sort(compute_trace_rows(trace); by = row -> string(row.property))
[(property = row.property, calls = row.calls,
  computed = row.computed, hits = row.hits) for row in rows]
4-element Vector{@NamedTuple{property::Symbol, calls::Int64, computed::Int64, hits::Int64}}:
 (property = :centered, calls = 2, computed = 1, hits = 1)
 (property = :energy, calls = 1, computed = 1, hits = 0)
 (property = :offset, calls = 1, computed = 1, hits = 0)
 (property = :scaled, calls = 4, computed = 2, hits = 2)

The figure is built from those same rows. Orange bars show requests answered from memory; blue bars show executions of a property body. A hit on scaled does not read centered again, because the stored scaled array already contains the result. That is why the counts at adjacent stages need not be equal, even though one stage depends on another.

julia
using AlgebraOfVega

counts = [(property = string(row.property), outcome = label,
           calls = getproperty(row, field))
          for row in rows for (label, field) in
          (("Computed", :computed), ("Memory hit", :hits))]
plot = data(counts) *
    mapping(:property => "Property", :calls => "Reads (count)";
            color = :outcome => "Outcome", dodge_x = :outcome) *
    visual(BarPlot) *
    config(height = 260,
           scales = scales(Color = (categories = ["Computed", "Memory hit"],
                                     palette = ["#2a78d6", "#eb6834"]),
                           Y = (zero = true,)),
           config = (axis = (labelFontSize = 14, titleFontSize = 14, labelAngle = 0),))

Fresh access ​

A fresh call bypasses the selected property's cache: it neither reads nor replaces that entry. Dependencies still use their ordinary access policy. Here the fresh scaled array has the same contents as the stored one but a different identity. The next ordinary call still returns the original array.

julia
uncached, fresh_trace = with_compute_trace() do
    fresh(signal.scaled, 2.0)
end
(first_is_cached = signal.scaled(2.0) === values.first,
 fresh_is_distinct = uncached !== values.first,
 same_values = uncached == values.first)
(first_is_cached = true, fresh_is_distinct = true, same_values = true)

Use this mode when a particular result should not be retained, or to compare one recomputation with a stored result. It does not refresh inputs for you. For a changed file, use tracked inputs; for changed constructor inputs, create a remade object as shown below.

Fresh access also leaves cached downstream values alone. Calling fresh(signal.scaled, gain) is not a request to replace the array that a previously computed energy(gain) used. Choose the operation according to the intended change: a one-off value needs fresh access; a stage that must be recomputed for subsequent readers needs invalidation. Keeping those operations separate matters when the result is an array shared by several consumers. A recomputation can allocate another array without withdrawing the one already held by earlier callers.

Invalidation ​

Clearing a property also clears values derived from it. Clearing centered therefore makes scaled and energy recompute, while retaining the independent offset value. The next trace makes that boundary visible.

julia
@clear_cache! signal.centered
_, after_clear = with_compute_trace() do
    signal.energy(2.0)
end
clear_rows = sort(compute_trace_rows(after_clear); by = row -> string(row.property))
[(property = row.property, computed = row.computed, hits = row.hits)
 for row in clear_rows]
4-element Vector{@NamedTuple{property::Symbol, computed::Int64, hits::Int64}}:
 (property = :centered, computed = 1, hits = 0)
 (property = :energy, computed = 1, hits = 0)
 (property = :offset, computed = 0, hits = 1)
 (property = :scaled, computed = 1, hits = 0)

The clear acts on the retained object; it does not change the formulas or the samples. Use this operation when a stage needs to be recomputed. To change the data itself, pass a replacement field to remake. The original object stays available for comparison, and properties dependent on the replaced field are computed for the new object.

For one indexed entry, invalidate!(signal.scaled, gain) removes that argument tuple. It does not express the broader instruction used here to recompute the dependent energy values. Choose property-wide invalidation when downstream cached results must also be withdrawn.

julia
changed = remake(signal; samples = [2.0, 3.0, 5.0, 6.0])
(original_offset = signal.offset, changed_offset = changed.offset,
 same_centered_values = signal.centered == changed.centered)
(original_offset = 3.0, changed_offset = 4.0, same_centered_values = true)

A constant shift changes the offset while leaving the centered values equal. The equality is a result of the formula, not evidence that a stale cache entry was carried over. Trace the remade object's first reads if you need to distinguish equal results from reused computations.
